# JU Portal Intake

How a project gets into the Portal. Explicit-command only — Founder drops
material in a local folder, gives one instruction, Builder packages it.

- Windows: `E:\JU_Portal_Inbox`
- WSL: `/mnt/e/JU_Portal_Inbox`

> The Inbox is a **local staging area**, not a runtime content source. Nothing in
> it is committed to this repository, and the deployed site never depends on it.
> Approved media is *copied into* this repo at publish time.

---

## Workflow

1. Founder creates a folder and fills in the request:

   ```bash
   /mnt/e/JU_Portal_Inbox/new-intake.sh <slug>
   ```

   This creates `incoming/<slug>/` with `PORTAL_REQUEST.md` and the optional
   evidence folders `release/`, `screenshots/`, `video/`, `remotion/`, `notes/`.

2. Founder drops real material into those folders. Empty folders are fine.

3. Founder says **"Portal 반영해"** (or "Portal Inbox 처리해").

4. Builder reads **only** `incoming/<slug>/`, creates a branch per the policy
   below, runs the existing checks and build, pushes, and returns a Preview.

5. Aside QA → Founder approval → merge / production.

6. After a **verified production release**, Builder moves the folder to
   `processed/YYYY-MM-DD_<slug>/` and adds `RESULT.md`.

Nothing merges automatically, and nothing is published without confirmation.

---

## Branch policy

**`main` is production only.** An Inbox request is never published directly to
`main`.

One branch per intake item, always created from the latest `origin/main`:

| request | branch |
|---|---|
| `action: add` | `portal/add-<slug>` |
| `action: update` | `portal/update-<slug>` |
| `action: promote` | `portal/promote-<slug>` |

```
portal/add-juminer
portal/update-juqode
portal/promote-judoctor
```

`feat/portal-v1-ui` was the initial UI build. It is **not** reused for Intake
work.

Sequence, in order:

1. fetch, start from latest `origin/main`
2. create the branch for that item
3. process only `incoming/<slug>/`
4. build media / Remotion if requested
5. update the authoritative Registry
6. run the existing tests and build
7. push the branch
8. produce a Vercel Preview
9. hand the Preview to Aside
10. wait for Founder approval
11. merge to `main` **only after approval**
12. verify Production
13. only then move the Inbox item to `processed/`

The Inbox item stays in `incoming/` until step 13. A Preview is not a release,
and a merge is not verified until Production has been checked.

### Multiple folders

Each Inbox folder is processed as its **own branch**, by default. Unrelated
products are not batched together.

They are combined into one branch only when the Founder explicitly says
**"한 번에 묶어서 반영해."**

---

## The hard intake rule

The Inbox decides **what** is processed. Builder does not go looking.

Builder MUST NOT:

- scan the Founder's other repositories
- independently discover projects
- crawl, watch, or poll for new material
- run on a schedule or as a daemon

GitHub may be opened **only** to verify something the request already points at:

- `source:` contains a URL, and the release or CTA needs verifying
- a CTA target must be confirmed reachable
- a licence or release asset must be confirmed

If `source:` is empty, GitHub is not opened. The Inbox is the work list.

## Request file

`PORTAL_REQUEST.md` at the root of each project folder:

```yaml
action: add          # add | update | promote
slug:                # lowercase kebab-case, unique in the Registry
section: lab         # product | lab | skill
source:              # repo / product URL
primary_action:      # what a user can actually do
remotion: make       # make | use | skip
note:
```

| field | rule |
|---|---|
| `action` | `add`, `update`, or `promote` |
| `section` | `product`, `lab`, or `skill` |
| `slug` | lowercase kebab-case, unique. Becomes a URL path and a media folder. |
| `source` | the only pointer that may authorise a GitHub lookup |
| `primary_action` | leave empty if there is none — that usually means `section: lab` |
| `remotion` | `make` (Builder generates), `use` (finished video supplied), `skip` |

---

## Product truth

A GitHub repository does **not** automatically become a Product.

To publish as `section: product`, all of these must be verified true:

- a real, reachable primary CTA (try / install / download / open)
- a public experience a beginner can actually reach
- the CTA target verified live
- a beginner-readable summary
- valid media, or an honest fallback

If any of those fail, Builder **stops and recommends `lab`**. Promotion is never
silent.

Labs carry no install or download control. That is the point of the section.

## Media

Priority, in order:

1. Founder-provided real video
2. Founder-provided real screenshots
3. actual app capture generated by Builder
4. Remotion generated from real assets
5. deliberate visual fallback

**An application screen is never fabricated.** If nothing real exists, the Portal
shows an explicit "not published yet" state rather than a convincing fake.

Builder-generated media lands in this repository under versioned paths, which are
mandatory because media is served `immutable`:

```
public/media/{slug}/overview.vN.mp4
public/media/{slug}/poster.vN.png
```

### Remotion

`remotion: make` — Builder owns producing the presentation video for that
request, from a reusable JU Portal template. Target 20–40 seconds:

| time | content |
|---|---|
| 0–3s | JU + product name |
| 3–8s | one-line problem / value |
| 8–25s | real screenshots or real product footage |
| 25–33s | 2–3 core outcomes |
| 33–40s | primary CTA / JU |

Only facts and visuals supported by the actual project. Nothing is invented to
fill a slot.

`remotion: use` — a finished video is already in `video/`; do not remake it.

`remotion: skip` — no video. The Portal uses a poster or fallback and publication
is not blocked.

## Publish

Publishing writes to the **authoritative Registry** in this repository:

| section | target |
|---|---|
| product | `content/products/{slug}.ts` |
| lab | the authoritative Labs registry |
| skill | the authoritative Skills registry |

Registry and `src/registry/action.ts` are Infra-owned. Builder does not bypass
the resolver and never invents a CTA URL. If a target cannot be verified, the
entry stays unresolved and renders "Coming soon" — never a broken link.

Per-request output:

```
INTAKE_ITEM · ACTION · SECTION · BRANCH · FILES_USED · MEDIA_CREATED
REGISTRY_CHANGED · CTA_VERIFIED · PREVIEW_URL · TESTS · BLOCKERS
```

Git hygiene: no force push, no rebase, no unrelated files in a commit, and a
dirty worktree is reported rather than swept into the change.

---

## Deliberately absent

This workflow is manual-triggered on purpose. There is no watcher, daemon,
cron, repository crawler, database, backend, CMS, or automatic publishing.

Founder drops material. Founder gives one instruction. Builder does the
packaging work.
